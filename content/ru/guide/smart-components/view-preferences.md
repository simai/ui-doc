# Персональный вид

Всё, что человек меняет во **внешнем виде** элемента, запоминается одинаково:
порядок, ширина, видимость и закрепление колонок, сортировка, размер страницы,
ширина панели. Для этого во Framework есть одно хранилище — `SF.Preferences`.
Без сервера вид хранится в браузере, а на сайте с личными настройками (Larena)
— ещё и у пользователя на сервере, и применяется до первой отрисовки: скелетон
уже стоит в порядке колонок человека.

## Что считается видом

- **Вид** — раскладка, порядок, размеры, видимость, сортировка, плотность,
  свёрнутость. Его хранит `SF.Preferences`.
- **Не вид** — данные и фильтры со значениями. Сохранённый набор фильтров — это
  именованное представление, которым делятся; оно хранится отдельно.

## Ключ и значение

Вид хранится под ключом `<компонент>/<экземпляр>`: `sf-table/cms.solutions`,
`sf-resizer/menu`. Экземпляр — постоянное имя того, что показывается
(коллекция, меню); его компоненту передаёт атрибут, например `preferences-key`
у таблицы или `storage-key` у [изменения ширины](/ru/smart-components/overlays/resizer/).
Без ключа ничего не запоминается: таблица-пример в документации остаётся
чистой.

Значение — обычный JSON-объект, которым владеет компонент; он читает только
известные ему поля и не перезаписывает значение более новой версии, которое не
понимает. У ширины панели это `{v: 1, width}` с шириной в пикселях. Значение
таблицы под `sf-table/<экземпляр>` складывается из полей, которые пишут
таблица и представление данных:

| Поле | Кто пишет | Что в нём |
|:---|:---|:---|
| `v` | оба | версия формата значения, `1` |
| `sort` | представление данных | `[{key, direction}]`, `direction` — `asc` или `desc`; пустой массив — без сортировки |
| `pageSize` | представление данных | размер страницы, целое число |
| `columnSettings` | таблица | раскладка колонок: `{<ключ колонки>: {order, width, visible, pinned}}` |
| `widths` | таблица | ширины колонок: `{<ключ колонки>: "<N>px"}` |
| `view` | таблица | плотность, полосы, линии, перенос и закрепление шапки; общие предпочтения `sf-table/*` несут только это поле |

## Где хранится

| Где | Когда | Как |
|:---|:---|:---|
| Браузер | всегда | `localStorage`, ключ `sf-pref:<ключ>`; это ещё и кеш для первой отрисовки |
| Сервер, у пользователя | когда страница подключила хранилище хоста | `SF.Preferences.useHost(adapter)`; значения хоста важнее браузерных |

Запись в браузер происходит сразу, на сервер — с задержкой 400 мс на ключ,
а при уходе со страницы всё, что ждёт, отправляется немедленно. Если вид
поменяли в другой вкладке, компоненты получают новое значение.

Компонент сам `localStorage` не трогает: это проверяет контракт Framework.

## Подключение хранилища хоста

`SF.Preferences` есть сразу после выполнения `core.js`, поэтому хранилище
хоста подключают встроенным скриптом сразу после него, до того как Loader
загрузит Smart-элементы:

```js
SF.Preferences.useHost({
  save: (key, value) => fetch(`/admin/preferences/${encodeURIComponent(key)}`, {
    method: 'PUT', headers: {'Content-Type': 'application/json'}, body: JSON.stringify(value), keepalive: true,
  }),
  remove: (key) => fetch(`/admin/preferences/${encodeURIComponent(key)}`, {method: 'DELETE', keepalive: true}),
  load: (keys) => fetch(`/admin/preferences?keys=${keys.map(encodeURIComponent).join(',')}`).then((r) => r.json()),
});
```

`save` обязателен, `remove` и `load` — нет. `load(keys)` возвращает обещание
объекта `{ключ: значение}`. `keepalive: true` нужен потому, что при уходе со
страницы отложенные записи отправляются из обработчика `pagehide`, и без него
браузер может оборвать запрос.

Чтобы и первый заход с нового устройства был в виде человека, сервер кладёт его
значения прямо в страницу — они читаются до первой отрисовки:

```html
<script type="application/json" data-sf-preferences>
  {"sf-table/cms.solutions": {"v": 1, "sort": [{"key": "updated", "direction": "desc"}], "pageSize": 50,
   "columnSettings": {"code": {"order": 10, "visible": true, "pinned": false, "width": "120px"}}}}
</script>
```

Блок может стоять в любом месте страницы до подключения компонентов: он
читается один раз, при первом чтении вида.

То же делает `SF.Preferences.preload(values)` из кода. Значения, которые
расходятся с браузерной копией, заменяют её, и компоненты перерисовываются.

## Чтение и запись

| Функция | Что делает |
|:---|:---|
| `read(key)` | значение под ключом: хоста, если он его дал, иначе браузера; сразу, без ожидания |
| `readMerged(...keys)` | несколько ключей от общего к частному, слитые по полям: `sf-table/*` (общие настройки таблиц человека) под `sf-table/<экземпляр>` |
| `write(key, value)` | записать вид |
| `remove(key)` | «Сбросить вид»: убрать из браузера и с сервера |
| `subscribe(key, fn)` | узнавать о новом значении — из другой вкладки или от хоста; возвращает функцию отписки |
| `load(keys)` | запросить у хоста ключи, которых он ещё не дал (компонент появился позже) |
| `flush()` | отправить отложенные записи сейчас |

## Раскладка таблицы: предпочтение и слой порта

У `<sf-data-view>` раскладку колонок помнят два места, и у каждого своя роль:

- **Предпочтение** `sf-table/<preferences-key>` — значение из таблицы выше.
  Оно читается до первой отрисовки, поэтому скелетон уже стоит в порядке
  колонок человека. Сортировка и размер страницы хранятся только здесь.
- **Личный слой порта** — `data.column_settings.layers.personal` в ответе
  приложения на запрос. При изменении колонок представление отправляет
  приложению намерение `settings.save_personal` с ревизией этого слоя, и
  приложение записывает раскладку у себя с проверкой ревизии.

Изменение колонок записывается в оба места сразу. На экране действуют
колонки из ответа приложения (`data.columns` с их порядком, шириной и
видимостью), а поверх них — предпочтение. Слои порта представление к таблице
само не применяет: ревизия слоя нужна ему для записи.

Поэтому приложение, которое хочет, чтобы раскладка человека была на любом
устройстве, делает одно из двух: подключает хранилище хоста и кладёт
значения в блок `data-sf-preferences`, или учитывает личный слой, когда
собирает `data.columns`. Ответ на запрос всегда несёт личный слой с
ревизией, даже пустой: без него запись колонок завершается ошибкой
(см. [Представление данных → Шаблоны и настройки колонок](/ru/smart-components/content/table/#шаблоны-и-настройки-колонок)).

## Уровни

Вид складывается из уровней, поздний уровень важнее по каждому полю:

1. значение по умолчанию компонента;
2. значение по умолчанию у хоста для экземпляра;
3. общие предпочтения человека для всех таблиц — плотность, полосы, перенос
   (`sf-table/*`);
4. вид человека для этого экземпляра (`sf-table/<экземпляр>`).

## Сброс

Компонент, который хранит вид, предлагает «Сбросить вид» там, где лежат его
настройки. Кнопка «Сбросить» в настройках таблицы убирает из значения
раскладку колонок (`columnSettings` и `widths`), а сортировку, размер
страницы и `view` оставляет; в `<sf-data-view>` она ещё записывает пустую
раскладку `{}` в личный слой порта против его ревизии. Ширину панели сбрасывает
двойной щелчок по ручке.

`SF.Preferences.remove(key)` из кода страницы стирает значение целиком и в
браузере, и у хоста, но открытую таблицу не перерисовывает: значения по
умолчанию она покажет после перезагрузки страницы.

## Какие компоненты уже хранят вид

- [Изменение ширины](/ru/smart-components/overlays/resizer/) — ширина панели
  под `sf-resizer/<storage-key>`.
- [Представление данных](/ru/smart-components/content/table/) — раскладка
  таблицы, сортировка и размер страницы под `sf-table/<preferences-key>`.
- Меню администратора Larena — ширины колонок и компактный вид.

[Вкладки](/ru/smart-components/navigation/tabs/) с `configurable` вид не
хранят: порядок и скрытые вкладки приходят событием
`sf-tabs-settings-change`, и приложение сохраняет их само — у себя или через
`SF.Preferences.write('sf-tabs/<ключ>', {order, hidden})` — и возвращает
методом `setSettings()`.
