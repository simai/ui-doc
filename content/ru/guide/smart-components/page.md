# На странице

Страница описывает работу с компонентом без сборок: в разметке и в коде
страницы. Настройки — это атрибуты и свойства, значения читаются у элемента,
события — обычные DOM-события, действия — методы элемента или кнопка с
`data-sf-action`.

## Подключение к странице

Смарт-компоненты лежат в поставке `ui`, в `distr/smart/`. Загрузчик находит
их по `window.sfPath`, который шаблон проекта задаёт один раз до подключения
`core.js` — см. [Порядок подключения](/ru/guide/connection/project-setup/#порядок-подключения)
и [Глобальные настройки](/ru/guide/connection/project-setup/#глобальные-настройки).
После этого на странице достаточно тега:

:::internal_preview {size="tall" title="Работающий пример"}
[Открыть демонстрацию](/demos/guide/smart-button/)
:::

:::code {src="../../../../examples/guide/smart-button/index.html" lang="html" title="index.html"}
:::

Увидев `<sf-button>`, загрузчик подключит смарт-кнопку и всё, от чего она
зависит. Подключать файлы каждого компонента вручную не нужно, и элементы,
которые появились позже, например после ответа сервера, загрузчик подхватывает
так же.

- Общая среда смарт-элементов приходит одна на страницу, вместе с первым
  компонентом — см. [Загрузка и общая среда](/ru/guide/smart-components/runtime/).
- Core и смарт-компоненты проект закрепляет одним выпуском и не смешивает
  файлы разных выпусков — см.
  [Выпуск и запись о выпуске](/ru/guide/connection/delivery/#выпуск-и-запись-о-выпуске).
- Компонент пакета подключается так же — тегом, но только на странице,
  которая объявила его пакет в `SF_BOOT_CONFIG.packages` до подключения Core.
  Если пакет не объявлен, загрузчик компонент не загружает и пишет в консоли,
  какой тег и почему. Так подключаются компоненты пакета `larena`:
  `<sf-table>`, `<sf-data-view>`, `<sf-property-view>`, `<sf-admin-menu>` и
  другие — см. [Пакет `larena` для проекта без Larena](/ru/guide/introduction/structure/#пакет-larena-для-проекта-без-larena)
  и [Пакеты партнёров и проектов](/ru/guide/smart-components/packages/).

## Ожидание готовности

Код, которому элемент нужен сразу после появления на странице, ждёт
определения тега:

```js
await SF.whenDefined('button'); // то же, что customElements.whenDefined('sf-button')
const button = document.querySelector('sf-button');
```

- Ждать нужно и тогда, когда скрипт компонента уже загружен: тег
  определяется, только когда пришла общая среда смарт-элементов.
- Настройки и значения элемента верны сразу после определения тега.
- `SF.whenDefined()` ничего не загружает: для тега, которого на странице нет,
  обещание не выполнится. Новый элемент создают через
  `await SF.createAsync('button')` — см.
  [События загрузчика](/ru/guide/connection/loader/#события-загрузчика).
- О каждой отрисовке элемент сообщает базовым событием `sf-after-render` —
  см. [Базовый интерфейс](/ru/guide/smart-components/model/#базовый-интерфейс).

## Пример

```html
<sf-switch id="notify" label="Уведомления" name="notify"></sf-switch>

<sf-modal id="confirm" label="Удалить запись?">…</sf-modal>
<button type="button" data-sf-action="confirm.open">Удалить</button>

<script>
  document.querySelector('#notify')
    .addEventListener('change', (event) => console.log(event.currentTarget.checked));
</script>
```

| Что | Где на странице |
|:---|:---|
| Настройка | атрибут тега (`label`, `size`); списки и объекты — свойство (`element.items = [...]`) |
| Значение | свойство элемента только для чтения: `element.checked`, `element.selected` |
| Событие | `addEventListener` на элементе |
| Действие | метод `element.open()` или кнопка `data-sf-action="<id>.<действие>"` |

## Имена событий

Имена и содержимое событий берутся из общего словаря — см.
[Имена и общие слова](/ru/guide/smart-components/names/). Манифест
объявляет событие **глаголом** (`close`, `saved`, `change`), а DOM-имя
выводит построение:

| Вид | Шаблон | Пример |
|:---|:---|:---|
| Просьба | `<тег>-<глагол>` | `sf-property-view-close` |
| Свершившийся факт | `<тег>-<глагол>ed` | `sf-property-view-saved` |
| Событие общей черты | `sf-<черта>-<глагол>` с `tag` в `detail` | `sf-field-reset` |
| Обычное событие браузера | своё имя при `"carries": "native"` | `change`, `input` |
| Событие компонента из пакета партнёра | `<тег>-<глагол>` с приставкой пакета | `acme-map-pick` |

Правила сборки слышат событие как `<роль>.<глагол>`. Имя вида `sf-…` в
списке `events` манифеста — ошибка: его выводят, а не пишут. Свой глагол
компонента помечен `"own-verb": true`, а его слово для людей лежит в файле
слов под `events.<имя>.label`.

- `detail` — всегда объект: `select {ids}`, `delete {ids, revisions}`.
- `detail` не несёт элементов страницы — только коды и данные.
- Двоеточий и суффикса `-intent` в именах нет. События с двоеточием
  (`sf-accordion:toggle`, `sf-menu:navigate`, `sf-field:reset`,
  `sf-code-input:complete` и другие) переходят на шаблон и сохраняют старое
  имя как псевдоним с датой.
- Одно действие — одно событие, и отправляет его компонент, которому
  действие принадлежит. Сборка не пересылает событие своей части как своё:
  шаг `emit` создаёт её собственное новое событие.

## Событие `change`

`change` сообщает о том, что **сделал человек**: изменил значение сам или
нажал кнопку, которая запустила действие, например сброс.

- Значение, заданное снаружи — настройкой, действием, сбросом формы, — обратно
  не сообщается. Так же ведут себя обычные поля HTML.
- Правило сборки, которому нужно и такое изменение, слушает `data.<ключ>`
  того ключа, к которому привязано значение.
- У поля формы `input` и `change` могут быть обычными событиями браузера
  (`"carries": "native"`). Они обязаны дойти до элемента-хоста, а слушатель
  читает значение у хоста, а не у `event.target`.

```js
const quantity = document.querySelector('#amount');
quantity.addEventListener('change', () => {
  // Читаем у хоста: внутри event.target может быть внутренний input.
  console.log(quantity.value);
});
```

## Просьбы, которые можно отклонить

Событие, которое компонент отправляет **до** того, как действовать, и ждёт
решения, объявлено `"cancelable": true`.

| Кто отклоняет | Как |
|:---|:---|
| Страница | `event.preventDefault()` |
| Правило сборки | шаг `refuse` — см. [Правила](/ru/guide/smart-components/rules/) |

После отказа действие компонента отвечает `refused`. Так устроены сброс поля
к наследуемому значению и закрытие окна.

```js
const editor = document.querySelector('#editor');
editor.addEventListener('sf-modal-close', (event) => {
  if (event.detail.unsaved && event.detail.reason !== 'api') {
    event.preventDefault(); // окно остаётся открытым
  }
});
```

## Кнопка `data-sf-action`

Атрибут `data-sf-action="<id элемента>.<действие>"` на кнопке страницы
запускает это действие без своего кода. Атрибут генерируется из списка
`actions` компонента и заменяет `data-sf-modal-*` и `data-sf-drawer-*`, которые
остаются псевдонимами.

```html
<sf-drawer id="filters" label="Фильтры">…</sf-drawer>
<button type="button" data-sf-action="filters.open">Фильтры</button>
<button type="button" data-sf-action="orders.refresh">Обновить список</button>
```

Тот же атрибут — единственный способ, которым обычное содержимое слота
просит сборку о чём-либо: см. [Слоты](/ru/guide/smart-components/slots/).

## Чего на странице нет

- Методов-читателей: всё, что нужно прочитать, — значение.
- Обращения к внутренностям сборки: страница видит только события самой
  сборки, а не её частей.
- Классов состояния, которые добавляет скрипт: состояние видно из разметки —
  см. [Разметка и шаблоны](/ru/guide/smart-components/markup/).
