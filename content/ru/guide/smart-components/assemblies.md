# Сборки

Сборка — компонент, составленный из других компонентов: экран, карточка,
панель. Внутри неё три понятия — **Детали**, **Данные** и **Правила**.
Снаружи у неё те же четыре части интерфейса, что у любой детали. Страница
описывает данные, роли, связи, раскладки, рамку и область экземпляра
сборки; правила — на отдельной странице.

## Пример: список записей с поиском

```json
{
  "id": "smart.record-list",
  "tag": "sf-record-list",
  "version": "1.0.0",
  "kind": "assembly",
  "family": "list",
  "settings": {"collection": {"type": "string"}},
  "values": {
    "selected": {"type": "string", "value": "chosen"},
    "total": {"type": "number", "value": "total"}
  },
  "events": {"open": {"carries": {"id": "string"}}},
  "actions": {"refresh": {}},
  "keys": {
    "collection": {"type": "string", "writer": "parent"},
    "query": {"type": "string", "writer": "search"},
    "items": {"type": "list", "writer": "source"},
    "total": {"type": "number", "writer": "source", "nullable": true},
    "state": {"type": "state", "writer": "source"},
    "chosen": {"type": "string", "writer": "logic", "initial": ""}
  },
  "roles": {
    "search": {"part": "sf-search-field", "bind": {"values.query": "query"}},
    "source": {"part": "sf-source", "bind": {"settings.collection": "collection", "settings.query": "query",
                                             "values.items": "items", "values.total": "total", "values.state": "state"}},
    "list": {"part": "sf-table", "bind": {"settings.items": "items", "settings.state": "state"}}
  },
  "layouts": {"default": {"file": "layout.default.html"}},
  "rules": [
    {"id": "r-open", "on": "list.open",
     "steps": [{"set": "chosen", "to": {"from": "id"}}, {"emit": "open", "with": {"id": {"from": "id"}}}]},
    {"id": "r-refresh", "on": "outside.refresh", "steps": [{"do": "source.refresh"}]}
  ]
}
```

flowchart TB
    subgraph links["Связи: деталь пишет ключ, другая читает"]
        direction LR
        search["Поиск"] --> query(["query"]) --> source["Источник"] --> items(["items"]) --> list["Список"]
    end
    subgraph moment["Правило r-open: когда открыли запись"]
        direction LR
        rule{{"set chosen — emit open"}} --> chosen(["chosen"])
        rule --> out["Наружу: событие open"]
    end
    list -- "событие open" --> rule
:::

Человек вводит текст в поиск → поиск пишет `query` → источник получает новый
запрос и пишет `items` → список перерисовывается. Это делают связи, без
единого правила. Правила нужны только для **моментов**: «когда открыли
запись — запомнить её и сообщить наружу», «когда снаружи попросили обновить —
попросить источник».

На стенде так собран целый экран полигона ui-admin — меню, заголовок
страницы, список записей с поиском, фильтром, порядком, страницами и
сохранёнными видами и панель записи с ленивыми разделами: три сборки
проходят проверку без ошибок и все 35 сценариев в браузере без единой
строки JavaScript под этот экран.

## Данные: у каждого ключа один хозяин

Сборка объявляет ключи. У каждого есть тип и ровно **один хозяин** — тот, кто
пишет ключ:

| Хозяин | Кто пишет ключ |
|:---|:---|
| имя роли | эта деталь, через связь своего значения |
| `parent` | родитель: ключ — одна из настроек самой сборки |
| `logic` | правила сборки; в Студии это «переменная» |
| `derived` | никто: ключ вычисляется из других ключей |

- Ключ с хозяином `logic` обязан иметь `initial` своего типа; его подпись
  берётся из файла слов (`keys.<ключ>`), а не из манифеста.
- Тип `state` хранит одно из семи состояний данных: `idle`, `loading`,
  `ready`, `empty`, `error`, `refused`, `unavailable`.
- Запись необъявленного ключа, запись не хозяином и запись не того типа
  отклоняются и попадают в журнал.
- У каждого экземпляра сборки свои ключи, поэтому одинаковые имена в двух
  сборках не мешают друг другу.

## Производные ключи

Ключ может вычисляться из других ключей:

```json
"keys": {
  "kind":       {"type": "enum", "values": ["person", "company"], "writer": "choice"},
  "is-company": {"type": "boolean", "writer": "derived",
                 "from": {"left": {"key": "kind"}, "op": "eq", "right": {"value": "company"}}},
  "total":      {"type": "number", "writer": "derived",
                 "from": {"sum": [{"key": "subtotal"}, {"value": 300}]}},
  "request":    {"type": "object", "writer": "derived",
                 "from": {"object": {"query": {"key": "query"}, "page": {"key": "page"}}}}
}
```

- `from` — чтение или условие, собранное только из закрытых списков правил:
  `sum`, `object`, `choose`, `eq`, `all` и других, см.
  [Правила](/ru/guide/smart-components/rules/#чтения-откуда-берётся-значение).
  Выражений, функций и циклов нет. То, чего ими не сказать, — вычисляемое
  значение в `behaviour.js` детали или работа хоста.
- Производный ключ никто не пишет: ни деталь, ни правило, ни родитель.
- Он считается после того, как записи хода применены, и до того, как связи
  их понесут, поэтому все детали видят одно согласованное состояние. Равный
  результат повторно не передаётся.
- Побочных действий у него нет. Цикл между производными ключами не
  пропускает проверка.
- Два правила, которые на одно событие ставят один флаг в `true` и в
  `false`, — это один производный ключ.

:::diagram {engine=mermaid title="Зависимая форма: выбор пишет kind, производный ключ is-company включает поле ИНН"}
flowchart LR
    choice["Выбор: лицо или компания"] --> kind(["kind"])
    kind --> derived{{"is-company — kind равно company"}}
    derived --> flag(["is-company"])
    flag -- "if" --> inn["Поле ИНН"]
:::

## Роли и связи

**Связь** — это состояние, а не момент. Она соединяет настройку части с
ключом (часть читает) или значение части с ключом (часть пишет). Часть,
поставленная позже, сразу получает текущее значение; равное значение повторно
не передаётся.

| Запись в `bind` | Направление |
|:---|:---|
| `"settings.<настройка>": "<ключ>"` | ключ → настройка части |
| `"values.<значение>": "<ключ>"` | значение части → ключ; часть становится хозяином ключа |

- Каждая связь сверяется с интерфейсом части.
- Часть, которая не может выполнить связи своей роли, на роль не встаёт.
- Части читают и пишут ключи и выполняют просьбы правил. Друг друга они не
  вызывают и событий друг друга не слушают.

У роли есть поля:

| Поле | Что задаёт |
|:---|:---|
| `part` | тег детали, можно со старшей версией: `"sf-table@2"` |
| `accepts` | интерфейс, который деталь должна реализовать: `"map-view@1"` |
| `bind` | связи с ключами |
| `settings` | постоянные настройки детали |
| `start` | когда деталь запускается — см. [Первый кадр и ленивая загрузка](/ru/guide/smart-components/first-paint/) |
| `if`, `hidden` | когда деталь убрана или скрыта — см. ниже |
| `each` | роль повторяется для каждой записи списка — см. ниже |

```json
"roles": {
  "inn":    {"part": "sf-input", "settings": {"name": "inn", "required": true}},
  "search": {"part": "sf-search-field", "bind": {"values.query": "query"}},
  "source": {"part": "sf-source", "bind": {"settings.query": {"key": "query", "debounce": 250}}},
  "map":    {"accepts": "acme-map-view@1", "part": "acme-map@1", "bind": {"settings.points": "points"}}
}
```

- **Постоянные настройки.** Роль может дать детали постоянные значения:
  `"settings": {"name": "inn", "required": true}`. Каждое сверяется с
  интерфейсом детали, как связь. Слово для людей постоянной настройкой
  манифеста не бывает: оно лежит в файле слов сборки под
  `roles.<роль>.settings.<настройка>`, и деталь получает его на своём языке.
  Настройку со словом связывают, как любую другую, с ключом, который держит
  данные: имя записи, фразу хоста.
- **Постоянные списки.** Варианты выбора, вкладки постоянного набора и
  столбцы таблицы роль даёт только значениями и ключами:
  `"options": [{"value": "open"}, {"value": "won"}]`,
  `"columns": [{"key": "title"}]`. Их слова лежат в файле слов — см.
  [Слова постоянных списков](/ru/guide/smart-components/language/#слова-постоянных-списков).
- **Задержка связи.** Связь может ждать: `{"key": "query", "debounce": 250}`.
  Ключ меняется сразу, а деталь получает значение через 250 мс без новых
  изменений. `debounce` — единственный оператор связи.
- **Старшая версия детали.** `"part": "sf-table@2"` закрепляет старшую
  версию. Деталь другой старшей версии отклоняется при загрузке с причиной
  `major-mismatch` и обеими версиями; подробнее — в разделе
  [Отпечаток договора](/ru/guide/smart-components/folder/#отпечаток-договора).
- **Несколько значений вместе.** Детали, которой нужны несколько значений
  сразу, удобнее читать один ключ-объект с одним хозяином, чем несколько
  ключей от разных хозяев.
- **Роль по интерфейсу.** `"accepts": "<интерфейс>@<старшая версия>"`
  проверяет деталь по `implements`, как содержимое слота. Деталь из пакета
  партнёра входит в сборку только так или через слот — см.
  [Пакеты партнёров и проектов](/ru/guide/smart-components/packages/).

## Показ и скрытие детали

```json
"roles": {
  "inn":  {"part": "sf-input", "if": "is-company", "settings": {"name": "inn", "required": true}},
  "note": {"part": "sf-textarea", "hidden": "!has-note"}
}
```

| Поле | Пока условие держится | Когда использовать |
|:---|:---|:---|
| `if` | `false`: деталь уходит из DOM, из значения формы и из проверки формы; экземпляр сохраняется со своим состоянием и возвращается с ним, а правила её роли не выполняются | деталь не относится к делу: ИНН компании для частного лица |
| `hidden` | `true`: деталь остаётся в DOM с атрибутом `hidden`, каждое поле формы внутри отключено — ничего не отправляет и не мешает отправке | деталь, которую человек может сразу вернуть |

- `if` и `hidden` называют логический ключ или его отрицание `!<ключ>`.
- `if="<ключ>"` на элементе раскладки равен `if` на каждой роли внутри него.
- Поле, скрытое только стилями, мешало бы отправке, которую человек не видит,
  и отправляло бы пустое значение. Поэтому скрывают через `if` или
  `hidden`, а не классом.

## Роль на каждую запись

```json
"roles": {
  "contact": {"part": "sf-contact-row", "each": "contacts",
              "bind": {"settings.name": "entry.name", "settings.phone": "entry.phone"}}
}
```

- `each` называет ключ-список, у записей которого есть `id`. Раскладка пишет
  `<x-role name="contact">` один раз, а роль повторяется для каждой записи в
  её порядке.
- Каждая деталь стоит на роли `contact[<код записи>]`; её `bind` может
  читать `entry.<поле>`.
- Детали сохраняются по коду при новом списке: запись, которая осталась,
  сохраняет элемент, введённые значения и идентификаторы. Деталь записи,
  которая ушла, убирается, и её область заканчивается.
- Правила слышат `contact.<событие>` от каждой записи, а чтение
  `{"entry": "<поле>"}` читает запись той детали, что отправила событие.
- Список меняют шаги `append` и `remove` или деталь, которая его пишет.
- Слот на каждую запись повторяет содержимое, которое даёт страница; роль на
  каждую запись повторяет детали, которыми владеет сборка.

### Внутри панели контейнера

Если `<x-role>` роли с `each` стоит внутри панели детали-контейнера —
элемента с `role="tabpanel"`, `<details>`, раздела `sf-accordion`, — вместе
с записью повторяется вся панель, в порядке записей и с
`data-entry="<код записи>"`. Контейнер берёт тот же список своими пунктами
и показывает панель выбранной записи.

```html
<x-role name="tabs">
  <div role="tabpanel"><x-role name="section"></x-role></div>
</x-role>
```

```json
"tabs":    {"part": "sf-tabs", "bind": {"settings.items": "sections", "values.selected": "current"}},
"section": {"part": "sf-field-group", "each": "sections", "start": "opened", "bind": {"settings.group": "entry.id"}}
```

- Панель пишется в раскладке один раз; проверка 4 смотрит, что её
  контейнер берёт список роли (`"settings.items": "<ключ из each>"`).
- Панель, которую контейнер закрыл, получает `hidden`, поэтому деталь
  `opened` в ней запускается, когда открыли её вкладку.
- Так панель записи на стенде берёт разделы у хоста: одна вкладка и одна
  деталь на раздел.

## Раскладки

Раскладка — HTML-шаблон сборки, который расставляет роли тегом `<x-role>` и
может показывать ключи. При смене раскладки детали переезжают вместе со
своим состоянием. `<x-role>` роли с `each` повторяется для каждой записи.

```html
<section class="flex flex-column gap-1">
  <header class="flex items-cross-center gap-1">
    <x-role name="search"></x-role>
    <span class="text-on-surface-variant">{{total}}</span>
  </header>
  <x-role name="list"></x-role>
  <x-role name="source"></x-role>
</section>
```

## Интерфейс сборки

Каждую часть интерфейса сборка получает так:

| Часть | Как её делают | Что внутри сборки |
|:---|:---|:---|
| `settings` | объявляют ключ с хозяином `parent` | этот ключ; правила могут реагировать на `outside.<настройка>` |
| `values` | у значения пишут `"value": "<ключ>"` | этот ключ; хозяин у него остаётся один |
| `events` | шаг `emit` в правиле | — |
| `actions` | объявляют действие | правила реагируют на `outside.<действие>` |

Родитель пользуется сборкой как обычной деталью: связывает её настройки и
значения, реагирует на её события, просит её действия. Что внутри, он не
видит.

Порт хоста страница передаёт один раз — верхней сборке, а до деталей
внутри его доводит рантайм, см.
[Порт внутри сборки](/ru/guide/smart-components/data/#порт-внутри-сборки).

## Рамка: ничего не выходит само

- События интерфейса частей останавливаются на сборке. Наружу уходит только
  то, что отправил шаг `emit`.
- Обычные события страницы границу проходят: `change`, `input`, `click` и
  другие события поля формы внутри сборки — это события DOM, а не события
  интерфейса. Проходит и событие интерфейса, объявленное
  `"carries": "native"`.
- Действие, которое не обработало ни одно правило, попадает в журнал, а не
  передаётся выше.
- Страница видит только собственные события сборки.

## Коды экземпляров

Код экземпляра — его **путь по ролям**:

| Где стоит | Код |
|:---|:---|
| На странице | `page/<id хоста или data-sf-role>` |
| Внутри сборки | `<код родителя>/<роль>` |
| Деталь на каждую запись | `<код родителя>/<роль>[<код записи>]` |

- Идентификаторы, которые пишут шаблоны (для `for`, `aria-controls`,
  `aria-labelledby`), строятся из пути: каждая последовательность
  не-буквенных знаков заменяется на `-`, затем `--<местное имя>`. Счётчик
  никогда не идентификатор: при перестановке двух экземпляров номера
  меняются, а серверная разметка не может их повторить.
- Экземпляр верхнего уровня без `id` и без `data-sf-role` — предупреждение;
  он получает код `<тег>[<n>]` по порядку в документе.
- Два одинаковых пути — ошибка в журнале; второй экземпляр не запускается.
- Экземпляр находит родителя по ближайшему хосту сборки в DOM, даже если тот
  ещё не определён, и его ходы ждут, пока родитель запустится.

## Что сборка говорит экранному диктору

У сборки, как у любого компонента, объявлены роль и имя в `accessibility`.
Значения, о которых она сообщает, перечисляет `accessibility.announces`, а
уровень заголовка она берёт из настройки `heading-level`. Подробно — на странице
[Доступность](/ru/guide/smart-components/accessibility/).

## Область экземпляра

У каждого экземпляра — детали, сборки, детали на каждую запись — одна
**область**: сигнал отмены (abort signal), который рантайм даёт его
поведению и его сборке.

- Всё, что экземпляр запускает, привязано к области: обработчики на
  странице и на других узлах, таймеры, запросы, потоки, наблюдатели,
  зарегистрированный слой.
- Область заканчивается, когда экземпляр убран: вынут со страницы и не
  поставлен снова в том же кадре, его запись ушла из роли на каждую запись
  или убрана его сборка. Всё привязанное отменяется сразу.
- Шаг, который ждал, когда область закончилась, отвечает `cancelled`.
  Изменение, уже отправленное хосту, не откатывается: его поздний ответ
  записывается в журнал и отбрасывается.
- Деталь вне DOM из-за `if` и деталь, которую переставила смена раскладки,
  свою область сохраняют.
- `behaviour.js` получает область и передаёт её всему, что запускает:

```js
// scope — сигнал отмены, который рантайм дал поведению экземпляра
window.addEventListener('resize', onResize, { signal: scope });
const answer = await fetch(url, { signal: scope });
```

Проверка 36 ставит и убирает экземпляр сто раз и считает, что осталось.

## Одна модель композиции

Во время работы композиция одна — сборка. Recipe и Document, документы
композиции Docara и Larena, либо компилируются в сборки — роли, ключи
стандартных типов, связи и правила, — либо остаются форматами хранения и
публикации. Своих области, связей, событий и правил во время работы у них
нет.

## История и сохранение

В рабочем режиме шина хранит только текущее состояние; её история — журнал
разработки. Ключ может включить:

| Флаг | Что даёт |
|:---|:---|
| `"undoable": true` | историю отмены и повтора |
| `"persist": "url"` | глубокие ссылки и кнопку «Назад» |
| `"persist": "local"` | вид, который запомнил человек |
| `"persist": "host"` | настройку, которую хранит приложение |

- **Сохраняет только верхняя сборка.** Ключи вложенной сборки живут в
  памяти, и журнал об этом говорит.
- **`undoable` в этой среде выполнения отложен:** ключ может его объявить,
  работает он и без него, а определение записывает об этом заметку.
- **У `persist: "host"` провода пока нет:** место, которое не `url` и не
  `local`, хранится в памяти с предупреждением в журнале.

## Шипы

Деталь может объявить шипы — связи по умолчанию с ключами словаря, в той же
форме, что `bind`:

```json
"connects": {"settings.items": "items", "settings.state": "state"}
```

- Поставленная в сборку, деталь связывается сама.
- Роль может переопределить шип.
- Шип называет постоянный ключ. Ключ, выбранный во время работы, шипом не
  бывает — так построение может проверить связь.
- Студия показывает то, что соединил шип, серой связью с пометкой «само»;
  человек может открыть и изменить её.
