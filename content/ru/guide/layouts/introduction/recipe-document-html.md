# Recipe, документ и HTML

У одной страницы три формы: правила сборки, готовое дерево и итоговая
разметка. Эта глава объясняет, что хранит каждая форма и какую из них
сохранять.

## Зачем три представления

У каждого представления своя работа.

| Представление | Что хранит | Кто с ним работает |
|:---|:---|:---|
| **Recipe** | правила сборки: шаблоны, места вставки, варианты, ссылки на настройки и содержимое | автор, редактор, продукт |
| **Document** | готовое проверенное дерево: варианты выбраны, данные подставлены, у узлов устойчивые идентификаторы | Framework, кеш, публикация |
| **HTML** | итоговая разметка | браузер |

Короче: **Recipe — инструкция, Document — результат сборки, HTML — вывод**.

Правила выбора:

- Recipe нужен, когда страница может выглядеть по-разному.
- Если вариантов нет, можно сразу хранить Document.
- HTML нельзя использовать как исходное описание страницы.

Recipe не обязательно писать вручную. Продукт может создавать его из своих
файлов: например, генератор статического сайта хранит Markdown и настройки, а
при сборке превращает их в Recipe. Автор правит исходники; Document и HTML создаются заново и не
становятся ещё двумя копиями страницы для ручной правки.

## Пример: статья с двумя шапками

Для статьи Recipe говорит: «возьми общий шаблон, выбери шапку по настройке и
вставь текст статьи». Настройка `headerMode` принимает `compact` или
`expanded`, а текст «Одинаковый основной текст.» приходит из одного источника
в обоих случаях.

```json
"select": {
  "value": {"input": "headerMode"},
  "cases": {
    "compact": {"id": "chosen-header", "ref": {"kind": "fragment", "owner": "example/library",
                "ref": "header.compact", "policy": "pinned", "revision": "r1"}},
    "expanded": {"id": "chosen-header", "ref": {"kind": "fragment", "owner": "example/library",
                 "ref": "header.expanded", "policy": "pinned", "revision": "r1"}}
  }
}
```

После сборки Document уже содержит выбранную шапку и текст. При `expanded`
его дерево такое: страница → секция с заголовком «Расширенная шапка» и
пояснением «Дополнительная строка шапки» → абзац «Одинаковый основной текст.».
При `compact` пояснения нет. Команды «выбери вариант» в Document нет: выбор
уже сделан. В браузере это две обычные статьи.

Переключите настройку в работающем примере и откройте «Собранный Document» или
«Полученный HTML», чтобы сравнить три представления на одних данных.

Полные Recipe, источники, оба набора настроек и ожидаемые Documents лежат в
[проверяемом JSON](/demos/guide/composition-recipe/header-switch.json). По нему

источники передаёт проект; Framework собирает дерево и создаёт HTML.

## Документ макета

Document имеет формат `simai.composition.document`. Его оболочка
одинакова для любого дерева:

| Поле | Смысл |
|:---|:---|
| `schema` | имя формата `simai.composition.document`, как в примере ниже; версию несёт `schema_version` (имя с меткой версии тоже принимается, см. [Имена и версии](/ru/guide/standards/map/#имена-и-версии)) |
| `schema_version` | версия формата: `1` |
| `id` | идентификатор документа |
| `profile` | `ui-layout` — интерфейс; `structured-content` — самостоятельный структурированный материал |
| `locale` | необязательный язык документа |
| `root` | единственный корневой узел |
| `extensions` | необязательные расширения с пространством имён |

Каждый узел дерева состоит из полей `id`, `type`, `data`, `props`, `slots`,
`presentation`, `bindings` и `extensions`. Других полей нет — неизвестное поле
отклоняется.

- `type` — зарегистрированный тип узла ([Тип узла](/ru/guide/layouts/introduction/levels/#тип-узла)).
- `data` — содержимое, например текст заголовка.
- `props` — настройки структуры, например число колонок.
- `slots` — именованные места для дочерних узлов ([Слоты и порядок](/ru/guide/layouts/building/slots/)).
- `presentation` — выбор оформления из закрытого списка: `view`, `preset`,
  `modifiers`.
- `bindings` — связь поля с внешним источником данных ([Привязки к источнику](/ru/guide/layouts/content-and-data/data-sources/#привязки-к-источнику)).

Пример ниже показывает минимальную информационную страницу:

```json
{
  "schema": "simai.composition.document",
  "schema_version": 1,
  "id": "about-page",
  "profile": "ui-layout",
  "locale": "ru",
  "root": {
    "id": "page",
    "type": "layout.page",
    "slots": {"default": [
      {"id": "intro", "type": "layout.section", "slots": {"default": [
        {"id": "title", "type": "content.heading",
         "data": {"level": 1, "content": [{"type": "text", "value": "О компании"}]}}
      ]}}
    ]}
  }
}
```

Обратите внимание: все `id` внутри документа уникальны. Документ ограничен:
до 1 МиБ в UTF-8, глубина вложенности до 32, до 2 000 узлов и до 500 детей в
одном слоте. Эти поля и ограничения сверяют при создании генератора, хранении
макета и разборе ошибки верхнего уровня.

**Расширения.** Расширение — ключ вида `пространство:имя`. Неизвестное
необязательное расширение сохраняется, но не исполняется. Расширение с
`required: true`, поддержку которого обработчик не объявил, останавливает
обработку: обработчик не делает вид, что понял документ.

Контрольный документ каталога показывает все части оболочки сразу:
структурированный текст со ссылкой, привязку к внешним данным, оформление
секции и расширение с пространством имён. Это контрольный пример Framework
`tests/fixtures/composition/catalog-page.json`: документация сверяет свою
копию с ним побайтно.
