# Первый кадр и ленивая загрузка

Человек должен видеть форму экрана с первого кадра, а загружаться должно
только то, что нужно сейчас. Для этого у компонента есть шаблон скелетона,
у сборки — первый кадр, составленный из скелетонов деталей, а у каждой
детали — момент запуска. Код и данные подчиняются одному правилу запуска.

## Шаблон скелетона

Рядом с `template.html` лежит `skeleton.html` — вид компонента, пока данных
ещё нет.

- Это те же элементы и классы, что в основном шаблоне, но текст, значения и
  картинки заменены полосками того же размера шрифта или заливками.
- Шаблон читает только настройки, никогда — данные. Повторяющиеся строки
  берут число из настройки.
- Рамка скелетона равна рамке готового вида при любых данных. Поэтому текст,
  длина которого зависит от данных, занимает заданное число строк: одну с
  многоточием или несколько с обрезкой и такой же минимальной высотой.
- Скелетону не нужен скрипт: это то, что видно до любого кода.
- Компоненту без данных с сервера отдельный скелетон не нужен: его первый
  кадр — статическая разметка.

```json
"presentation": {"skeleton": {"file": "skeleton.html", "repeat": {"rows": "page-size"}}}
```

## Первый кадр сборки

Скелетон сборки не рисуют вручную — его составляет построение SIMAI
Framework. Для каждой раскладки и каждого примера:

- место каждой роли получает статическую разметку детали, если её данные
  известны заранее, иначе — её `skeleton.html` с числом строк из настроек
  роли;
- результат поставляется как `static/<раскладка>/<пример>.html`, а
  `static/sheets.json` перечисляет стили **всех** деталей, запущенных и нет:
  вид детали нужен для скелетона, её код — нет;
- в заголовок страницы печатаются `<link rel="modulepreload">` для ядра и для
  деталей, которые запускаются сразу. На медленной сети это сократило время
  до полезного экрана с 2,5 до 1,5 с.

## Три фазы без сдвигов

| Фаза | Что видит человек |
|:---|:---|
| пришли HTML и стили | скелетон всей сборки — первый кадр |
| пришёл код | каждая деталь подхватывает свою разметку в той же рамке |
| пришли данные | скелетон превращается в содержимое за один кадр |

Между фазами ничего не сдвигается. Проверка 24 сравнивает рамки скелетона
и готового вида каждой детали на ширине компьютера и телефона.

## Когда запускается деталь

Роль в сборке может указать момент запуска:

```json
"roles": {
  "head":    {"part": "sf-record-head", "start": "now"},
  "history": {"part": "sf-record-history", "start": "visible"},
  "access":  {"part": "sf-field-group", "start": "opened"}
}
```

| `start` | Деталь запускается |
|:---|:---|
| `now` (по умолчанию) | вместе со сборкой |
| `visible` | когда её рамка впервые попала на экран |
| `opened` | когда открыли её вкладку, раздел, пункт аккордеона, окно или панель |

## Одно правило для кода и данных

Пока деталь не запущена:

- её код не загружается ради неё;
- она ничего не просит у хоста, а данные, которые читают только незапущенные
  детали, не запрашиваются;
- правила её роли не выполняются, а её события не копятся;
- она показывает свой первый кадр с `aria-busy="true"`.

После запуска:

- запущенная деталь остаётся запущенной: закрыли и открыли вкладку — ничего
  не загружается заново;
- общий код нескольких ролей приходит с первой из них, остальные ждут своего
  запуска;
- момент запуска решает сборка, а не деталь;
- то, что открывает отложенную деталь, не откладывается никогда: вкладки,
  заголовки разделов и кнопки окон сразу доступны с клавиатуры и для
  экранного диктора. Вкладки над отложенными панелями открываются по Enter
  или пробелу, стрелки только переводят фокус.

У любого элемента есть базовые значения `shown` (деталь видна в открытом
контейнере) и `started` (сборка её запустила); на элементе они видны как
`data-sf-started` и `data-sf-start`.

## Один раздел записи

Карточка записи показывает один раздел. Если порт хоста умеет
`group.load {record_id, group, reason}` (возможность `group-load`), первый
ответ несёт заголовок записи, её версию, устройство разделов и поля одного
раздела, а каждый следующий раздел просит свои поля при открытии. Хост без
этой возможности работает как прежде: адаптер один раз просит всю запись и
раздаёт разделы из этого ответа. На стенде это уменьшило данные при открытии
с 24,5 до 2,4 КБ.

## Где это нужно

- карточка записи: разделы и вкладки;
- аккордеоны и вкладки с тяжёлым содержимым;
- окна и боковые панели: содержимое при открытии;
- длинные страницы и панели админки с несколькими виджетами;
- таблица ниже первого экрана;
- страницы документации с десятками примеров.
