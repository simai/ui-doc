# Данные с сервера

Данные приходят от хоста — приложения, в котором стоит компонент: Larena,
решения Bitrix, чата. Компонент не строит запросы сам: он говорит глаголами
словаря, а с портом хоста разговаривает сгенерированный адаптер. Страница
описывает порт, источник, ответы хоста, состояния данных, изменения и
потоки.

## Порт

Компонент, который говорит с хостом, объявляет свой порт:

```json
"port": {"id": "simai.dataview-port", "version": "1.12",
         "contract": "contracts/ports/dataview-port/1.12.0/port.json"}
```

- Действия такого компонента называются глаголами словаря: `refresh`,
  `save`, `delete`, `load-more`.
- **Построение генерирует по одному адаптеру на порт.** Адаптер переводит
  глаголы и их содержимое в намерения порта (`sequence`, объект `query`,
  `revisions` по кодам, `action_id`), а ответы порта — в ответы словаря.
- Сам компонент никогда не собирает содержимое запроса к порту.
- Страница передаёт порт базовым действием `connect-port {port}`.

```js
const orders = document.querySelector('#orders');
orders.connectPort({ port: window.app.dataViewPort });
```

### Порт внутри сборки

`connect-port` на сборке обрабатывает рантайм, а не правила. Сборка хранит
порт и передаёт его каждой детали на любой глубине, чей манифест объявляет
порт с этим `id`, — и деталям, поставленным позже: роли на каждую запись,
детали, вернувшейся по `if`, детали, которая запускается при открытии.

- Страница передаёт каждый порт один раз — верхней сборке.
- Деталь, которой порт так и не передали, отвечает `unavailable` с причиной
  `port-not-connected`.
- Правило порт не несёт: чтения правил — данные.

На стенде экрана админки четыре детали с портом стоят на один и два уровня
внутри сборок; без этого страница передавала бы порт каждой из них вручную.

Словарь не переименовывает намерения портов: это версионированные договоры с
серверным кодом на другой стороне, и переименование было бы новой старшей
версией порта.

**Данные без запроса.** Порт может прислать данные сам: растущий ответ,
новое сообщение, ход долгой задачи. Адаптер отдаёт их компоненту, который
держит порт. Компонент пишет свои значения и сообщает о присланном
событиями-фактами потока (см. ниже), а не `change`: `change` сообщает о
действиях человека. Каждая такая присылка начинает свой ход с пустой
цепочкой причин.

## Источник `sf-source`

В сборке данные приносит деталь на роли `source`. Она берёт `collection`,
`query`, `filters`, `sort`, `page` и `page-size`, спрашивает хост через порт, применяет
только самый новый ответ (её чтения идут с `concurrency: latest`) и
вычисляет состояние данных. О присланном без запроса и о потоках она
сообщает событиями-фактами.

| Значение источника | Ключ сборки | Что значит |
|:---|:---|:---|
| `items` | `items` | записи |
| `total` | `total` | число записей; `null` — ещё не посчитано |
| `total-exact` | `total-exact` | `false`, если `total` приблизительное |
| `has-more` | `has-more` | есть ещё записи; вычисляется, хост его не присылает |
| `state` | `state` | состояние данных |
| `message`, `reason` | `message`, `reason` | фраза хоста и его код при любом ответе, кроме `applied` |

- `page` — номер страницы с 1, а `page-size` — число записей на странице,
  оба числа, как их даёт `sf-pagination`; страничная навигация по
  продолжению читает ключ записи `cursor`.
- `sort` — список `[{key, direction}]`, первым идёт главный столбец, как
  его возвращает порт представления данных.
- Новый запрос сам страницу не сдвигает: на первую её возвращает правило.

Компонент без побочного эффекта `network` в сеть не ходит: данные приходят
только через источник или порт хоста.

## Ответы хоста

На каждую просьбу хост отвечает одним из четырёх ответов:

| Ответ | Значит | В Larena по HTTP |
|:---|:---|:---|
| `applied` | сделано | 200 |
| `conflict` | запись уже изменили; вот текущая версия | 409 |
| `refused` | нельзя: нет прав или неверные данные; с причиной | 422 |
| `unavailable` | хост не ответил или возможности нет | остальное, например 503 |

Хост состояние не присылает: он отвечает, а источник переводит ответ в
состояние. Причины сравниваются без различия `-` и `_`:
`access-denied` и `access_denied` — одна причина, потому что эталонный хост
и Larena пишут их по-разному.

Пятый исход записывает сама ждущая сторона, хост его не присылает:

- **`cancelled`** — ожидание остановил человек, его заменил более новый
  запуск или экземпляр убрали со страницы. Это поступок, а не сбой: ветка
  «иначе» не выполняется, и состояние списка не меняется.
- Ждущая сторона пишет и две причины: `busy` — у `refused`, когда правило с
  `drop` отбросило просьбу, пока шёл прежний запуск; `timeout` — у
  `unavailable`, когда ожидание превысило свой `timeout`.

## Семь состояний данных

`idle`, `loading`, `ready`, `empty`, `error`, `refused`, `unavailable` —
состояние данных всегда одно из семи, и компонент показывает каждое сам.

| Ответ хоста | Состояние |
|:---|:---|
| `applied` с записями | `ready` |
| `applied` без записей | `empty` |
| `refused` с причиной доступа (без причины, `forbidden`, `access_denied`, `scope_denied`, `*_access_denied`, `*_scope_denied`) | `refused` |
| `refused` с любой другой причиной (`query_invalid`, `sort_invalid`, `settings_invalid`, `view_unknown` и другие) | `error` с `message` хоста; панель инструментов и запрос остаются |
| `unavailable` (`collection_unavailable`, `capability-not-provided`) | `unavailable` |
| сбой сети, HTTP 5xx | `error` |

:::diagram {engine=mermaid title="Семь состояний данных: из loading в одно из пяти по ответу хоста; новый запрос или повтор снова ведёт в loading"}
flowchart LR
    idle(["idle"]) -- "запрос" --> loading(["loading"])
    loading --> ready(["ready — есть записи"])
    loading --> empty(["empty — записей нет"])
    loading --> refused(["refused — нет доступа"])
    loading --> error(["error — ошибка или сбой"])
    loading --> unavailable(["unavailable — хост не ответил"])
:::

- `idle` — ещё не спрашивали, `loading` — ждём ответа.
- `ready` заменяет `populated`; старое слово остаётся псевдонимом с датой.
- «Загружается ещё» — не состояние: это `has-more` вместе с идущим
  `load-more`.
- В ленте и поле ввода сообщения `refused` на открытом разговоре (доступ
  отозван) ещё и очищает черновик и неотправленные записи.

## Изменения и конфликты

Изменение тоже получает ответ, а не состояние: `applied`, `conflict`,
`refused` или `unavailable`.

**Изменения** — это глаголы, которые меняют данные хоста: `save`, `delete`,
`create`, `rename`, `archive`, `restore`, `move`, `apply`, `submit`,
`retry`, `attach`, `detach`, `answer`, `rate`, `read`. Остальные глаголы
читают или действуют на месте. Изменение никогда не запускают с
`concurrency: latest`: прерванное изменение могло уже выполниться на хосте.

- Каждое изменение несёт `revision` записи — версию для сравнения и замены.
  Повтор сохраняет **исходную** версию; массовые изменения несут `revisions`
  по кодам.
- `client-key` — постоянный ключ изменения: повтор с тем же ключом — то же
  изменение. Ключ делает источник, а не правило.
- **Одна версия на запись.** Разделы записи делят её версию: `group.load`
  отвечает версией всей записи, `group.save` сравнивается с ней, а своей
  версии у раздела нет. Сохранение по более старой версии отвечает
  `conflict` с текущей.
- `conflict` приходит с текущей версией. Если её нет (так отвечает порт
  представления данных 1.12), источник перечитывает список.
- Массовый конфликт несёт `conflicts [{id, current-revision}]`, а
  изменившееся число — `current-total`. Larena присылает `conflicts`
  объектом `{id: revision}`; источник читает обе формы.
- `refused` с `confirm_required` несёт `confirm {summary, digest}`. Изменение
  повторяют с `confirm: <digest>` после ответа роли `confirm` — и массовое
  изменение `apply` тоже.

## Две формы ответа

Источник читает обе формы ответов, которые есть у портов:

```json
{"answer": "applied", "reason": null, "message": null,
 "data": {"records": [], "total": 1240, "total_exact": false, "has_next": true, "next_cursor": null}}
```

```json
{"answer": "conflict", "record": {"id": "42"}, "revision": "7", "errors": [], "reason": "stale", "message": "Запись изменили"}
```

Первая — у порта представления данных, вторая, плоская, — у порта
просмотра свойств. Запросы порта представления данных несут `sequence` и
объект `query`; их пишет адаптер, а не компонент.

## Потоки

Растущий ответ (ответ ИИ), загрузка файла и долгая задача живут по одной
схеме. Компонент, который держит порт, сообщает о потоке фактами, и каждый
несёт `id` записи:

| Факт | Слово | Что значит |
|:---|:---|:---|
| `begun {id}` | начато | поток начался; у записи `growing` — да |
| `chunk {id, …}` | часть | пришла часть: текст или `done` и `total` загрузки или задачи |
| `completed {id}` | завершено | поток закончился целиком |
| `failed {id, reason, message}` | не удалось | поток закончился ошибкой |
| `cancelled {id}` | отменено | поток остановил человек или закончилась область экземпляра |

:::diagram {engine=mermaid title="Жизнь потока: начало, части, ровно один конец — завершено, не удалось или отменено"}
flowchart LR
    start(["begun"]) --> growing["Пишется — приходят части chunk, growing да"]
    growing -- "completed" --> done["Завершено"]
    growing -- "failed" --> failed["Не удалось"]
    growing -- "cancelled" --> cancelled["Отменено"]
:::

- Факт начала потока — `begun`: имя `started` занято базовым значением
  элемента «сборка его запустила».
- Поток заканчивает ровно один из фактов `completed`, `failed` и
  `cancelled`, и `growing` становится ложным. Список при этом остаётся
  `ready`, а растущая запись рисуется с `aria-busy`.
- Действие, которое начинает поток (`submit`, `attach`), отвечает, когда
  поток начался, а не когда закончился. Правила, которым нужен конец,
  слушают `completed`, `failed` или `cancelled`.
- `cancel {id}` просит хост перестать писать. Если хост этого не умеет,
  компонент только перестаёт ждать: больше не применяет рост и заканчивает
  поток `cancelled`.
- Каждая часть меняет запись заплаткой по коду. Версия записи растёт с
  каждой частью, или список объявляет `changes: content` — см.
  [Записи: строки и узлы](/ru/guide/smart-components-2/entries/#много-записей).
- Каждая присланная часть — свой ход.

**Чат.** У чата свои слова ожидания ответа ассистента. `stop {conversation,
id?}` значит «перестать ждать»: после `applied` источник перестаёт
показывать рост ответа, запись получает `wait: stopped`, а поток
заканчивается `cancelled`. Сервер при этом может дописать ответ. Остановить
само написание — возможность порта `reply-cancel`, её просит `cancel {id}`.
Поле `wait` принимает `delayed`, `stopped`, `network` или `none`; `null`
читается как `none`.

## Приблизительное число «~N»

Если хост посчитал записи приблизительно (`total-exact: false`), показанное
число читается как «~N»: «~1 240 записей». Пока число приблизительное,
действие над всеми записями под фильтром не применяется: для него нужны
подтверждённое число, применённые фильтры и возможность
`bulk-under-filter`.
