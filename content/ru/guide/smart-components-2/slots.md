# Слоты

Слот — место в компоненте, куда страница вставляет своё: текст, кнопки,
целый блок или деталь с нужным интерфейсом. Слоты бывают и у деталей, и у
сборок. Главное правило: содержимое страницы остаётся содержимым страницы.

## Объявление

```json
"slots": {"content": {"default": true}, "footer": {}, "label": {"replaces": "label"}}
```

```html
<sf-modal id="edit" label="Правка записи">
  <form slot="content">…</form>
  <div slot="footer">
    <button type="button" data-sf-action="edit.close">Отмена</button>
  </div>
</sf-modal>
```

| Поле | Что значит |
|:---|:---|
| `default` | сюда попадает содержимое без атрибута `slot` |
| `replaces` | содержимое слота побеждает текст названной настройки |
| `accepts` | слот принимает деталь с интерфейсом — см. ниже |
| `each` | слот повторяется для каждой записи — см. ниже |
| `bind` | связи вставленной детали, как у роли |

## Обычный слот

- Компонент **ставит** содержимое на место и никогда не копирует и не
  пересобирает его из HTML-строки. Поэтому у содержимого сохраняются
  обработчики страницы, состояние и сама идентичность узлов.
- События из содержимого слота — события страницы, а не компонента. До
  правил компонента они не доходят.
- Обычное содержимое просит сборку только через её публичные действия:
  `data-sf-action="<id хоста>.<действие>"`, а не через её правила.

## Слот, который принимает деталь

```json
"slots": {
  "detail": {"accepts": "record-view@1", "bind": {"settings.record-id": "chosen"}}
}
```

- **Что называет `accepts`.** Интерфейс `<имя>@<старшая версия>`: общую черту
  или папку интерфейса той же формы.
- **Что подходит.** Содержимое, в манифесте которого интерфейс указан в
  `"implements"` с той же старшей версией и объявлены все настройки, события
  и переносимые поля интерфейса тех же типов.
- **Имена событий** задаёт интерфейс: `sf-<интерфейс>-<глагол>`, какой бы ни
  был тег содержимого.
- **Когда проверяется.** После того как элемент содержимого определён.
  Сборка ждёт определения до предела — по умолчанию 1,5 с.
- **Связи.** У слота с `accepts` есть `bind`, как у роли. Деталь стоит на
  роли `<слот>`, а правила слышат `<слот>.<событие>`.

## Отказ

Неподходящее содержимое и содержимое для слота, которого компонент не
объявил, отклоняются:

- оно не ставится на место и не связывается;
- остаётся в хосте скрытым, с атрибутом `data-sf-refused="<причина>"`;
- журнал записывает слот, тег и причину.

| Причина | Что не так |
|:---|:---|
| `no-interface` | в манифесте нет `implements` |
| `other-interface` | реализован другой интерфейс |
| `major-mismatch` | не та старшая версия |
| `missing-setting` | нет настройки интерфейса |
| `missing-event` | нет события интерфейса |
| `carries-mismatch` | переносимое поле другого типа |
| `not-defined` | элемент не определился за отведённое время |
| `needs-template` | слоту на каждую запись дали не `<template>` |
| `unknown-slot` | компонент не объявлял такой слот |

## Слот на каждую запись

Один узел не может стоять сразу в нескольких строках, поэтому слот,
повторяемый для каждой записи, штампует шаблон, а не ставит узел страницы.

```json
"slots": {
  "row-tools": {"accepts": "row-tools@1", "each": "items",
                "bind": {"settings.record-id": "entry.id"}}
}
```

```html
<sf-record-list id="orders">
  <template slot="row-tools">
    <sf-row-tools></sf-row-tools>
  </template>
</sf-record-list>
```

- Слот с `"each": "<ключ списка>"` принимает один `<template>`; остальное
  отклоняется с причиной `needs-template`.
- Сборка штампует шаблон для каждой записи и связывает каждый оттиск по
  `bind` слота: `"settings.record-id": "entry.id"`.
- Оттиски привязаны к коду записи и сохраняются при перерисовке.
- Обработчики страницы в оттиски не переносятся; связывается только
  объявленный интерфейс.
- Деталь в оттиске стоит на роли `<слот>[<код записи>]`.
- Слот с `each` без `accepts` — просто повторяемое содержимое.
