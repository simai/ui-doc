# Папка компонента и манифест

Страница для авторов компонентов: где компонент делают, как устроена его
папка, что в ней пишет человек и что генерирует построение (build), какие
имена заняты, как выглядит полный манифест `component.json`, как он
сохраняется и как построение следит за изменением интерфейса.

## Где делают компоненты

Слои идут сверху вниз, зависимости смотрят только вниз:

:::diagram {engine=mermaid title="Слои компонентов: продукты используют ui-pro и SIMAI Framework, ui-pro зависит от SIMAI Framework; зависимости смотрят только вниз"}
flowchart TB
    products["Продукты и эталонные приложения"]
    partners["Пакеты партнёров и проектов"]
    pro["ui-pro — продвинутые и общие компоненты"]
    framework["SIMAI Framework — базовые блоки"]
    products -->|используют| pro
    products -->|используют| framework
    partners -->|зависят от| pro
    pro -->|зависит от| framework
:::

Продукты — это Larena, решения Bitrix, почта и чат, эталонные приложения —
ui-admin и ui-chat. SIMAI Framework выходит под лицензией Apache-2.0.

- Компоненты SIMAI делают **только в двух местах**: в SIMAI Framework —
  базовые, в ui-pro — продвинутые и общие. Набор имён `sf-` растёт только
  через ui-pro.
- Продукт и эталонное приложение своих наборов компонентов не делают. Если
  нужного компонента нет, его делают в ui-pro, а базовый — в SIMAI Framework.
- Экраны продукта — это **сборки** из этих компонентов, описанные продуктом,
  а не новые теги. Экран, который стоит переиспользовать, переезжает в ui-pro
  как компонент.
- ui-pro зависит от SIMAI Framework; SIMAI Framework ни от чего выше себя не
  зависит.
- Партнёр или проект заказчика может выпустить свой пакет компонентов под
  своей приставкой. Пакет зависит от SIMAI Framework или ui-pro, но не
  наоборот — см.
  [Пакеты партнёров и проектов](/ru/guide/smart-components-2/packages/).

## Одна папка

Компонент живёт в одной папке с именем тега без приставки: `sf-button` →
`button/`. По стандарту 1.4 человек пишет в ней **пять файлов**, а всё
остальное делает построение (build).

:::diagram {engine=mermaid title="Папка компонента 1.4: пять файлов пишет человек, остальные генерирует построение"}
flowchart LR
    subgraph authored["Пишет человек"]
        direction TB
        manifest["component.json — договор"]
        examples["examples.json — примеры"]
        code["index.js и js — код"]
        words["lang — слова по языкам"]
        text["docs.md — текст"]
    end
    build(["Построение"])
    subgraph generated["Генерирует построение"]
        direction TB
        rule["rule.js и aliases.json"]
        registry["smart.manifest.json и meta.mjs"]
        studio["studio.fixture.json и studio.scenario.json"]
        probe["probe.json"]
        snapshots["static — снимки начального вида"]
    end
    manifest ~~~ examples ~~~ code ~~~ words ~~~ text
    rule ~~~ registry ~~~ studio ~~~ probe ~~~ snapshots
    authored --> build
    build --> generated
:::

**Пишет человек:**

| Файл | Что хранит |
|:---|:---|
| `component.json` | манифест — единственный источник договора. С 1.4 в нём же связи загрузчика (`relations`), псевдонимы старых имён (`aliases`), правило загрузчика (`x-rule`) и то, что пока знает только реестр (`x-registry`) |
| `examples.json` | примеры в виде `{"examples": […]}`, пример для Студии (`studio`) и страница соответствия (`pages`) |
| `index.js` и папка `js/` | код элемента: поведение и шаблоны |
| `lang/<язык>.json` | слова для людей, по файлу на язык |
| `docs.md` | один текст на языке документации |

Если нужны стили сверх классов и токенов SIMAI Framework, рядом лежит папка
`scss/`. `skeleton.html` пишут, только где скелетон, выведенный из снимка,
неверен; сегодня такой один — у `sf-profile-picker`.

**Генерирует построение:**

| Файл | Из чего | Кто читает |
|:---|:---|:---|
| `rule.js` | `relations` и `x-rule` | загрузчик |
| `aliases.json` | `aliases` | псевдонимы старых имён с датами |
| `smart.manifest.json` | `component.json`, `lang/`, `rule.js` | реестр: справочник на этом сайте, каталог Студии, подсказки ui-vscode |
| `meta.mjs` | настройки и их слова | Студия: описание атрибутов |
| `studio.fixture.json`, `studio.scenario.json` | пример `studio` | Студия |
| `probe.json` | страница соответствия `pages` | проба соответствия в браузере |
| `static/<шаблон>/<пример>.html`, `static/sheets.json` | примеры, снятые в браузере | начальный вид, см. [Первый кадр](/ru/guide/smart-components-2/first-paint/#снимок-при-построении) |

- Сгенерированные файлы пока лежат в папке и коммитятся рядом с
  исходными, но руками их не правят: проверка построения сравнивает каждый
  с тем, что дало бы построение, и не пропускает расхождение.
- Генератор — `scripts/generate-component-files.mjs` в simai/ui-source:
  `--check` только сравнивает, `--write` записывает. Ключ `--package`
  запускает его над папками пакета.
- Снимки начального вида снимаются заново одной командой, когда меняется
  вид (см. [Правила для авторов](/ru/guide/smart-components-2/authors/)).

Сборка добавляет файлы раскладок `layout.<имя>.html` и раздел `rules` в
манифесте.

Страница документации компонента — это текст `docs.md`, за ним
сгенерированный справочник и сгенерированные примеры. Больше для неё ничего
не пишут: второго текста рядом с `docs.md` нет.

Файлов, которые только импортируют другие файлы ради точки входа, нет.

**Зачем пять файлов.** Когда справочник, Студия и проба повторяют договор
своими файлами, они расходятся с `component.json`: в реестре вида 1.3 у
`sf-button` не было события `press`, у `sf-tree` — шести событий версии
2.0, у `sf-table` — тринадцати настроек списка, и эти ошибки видели
справочник на сайте, каталог Студии и подсказки редактора. По стандарту 1.4
всё это выводится из одного файла. Человек держит меньше: у `sf-button` 5
файлов договора вместо 12 (1189 строк вместо 1728), у `sf-tree` — 5 вместо
11.

**Где компоненты сегодня.** Все смарт-компоненты SIMAI Framework — в виде
1.4 с выпуска `ui-e84590925e63` (первые тридцать — в `ui-83158c9c9538`):
каждый генерирует все свои файлы байт в байт. Одиннадцать компонентов ui-pro
пока в прежнем виде. Шаблон-разметка `template.html` остаётся целью:
большинство компонентов рисует разметку в JavaScript (`js/templates/`).
Начальный вид от этого не зависит — снимок записывает то, что рисует живой
элемент, и компонент, который перенесёт разметку в шаблон, сохранит тот же
снимок. Отдельным переносом это не считается.

## Зарезервированные имена

Настройку, значение, событие, действие, ключ данных или роль нельзя назвать:

- `props`, `api`, `view`, `scope`, `parts`, `receive`, `render`, `connected`,
  `disconnected`, `updated`, `outside`, `data`;
- именем из базового интерфейса (`template`, `focus`, `blur` и другими);
- именем, которое начинается с `_` или `sf`;
- именем, которое в camelCase совпадает со свойством `HTMLElement.prototype`
  или его предков: `id`, `role`, `title`, `hidden`, `slot`, `children`,
  `part`, `lang`, `dir`, `style`, `dataset` и остальные.

Последний пункт взят из опыта: настройка `id` забирала DOM-идентификатор,
`children` — геттер, который бросает ошибку, а `role` превращался в
ARIA-атрибут. Проверка манифеста берёт этот список у прототипа в браузере, а
не из копии.

**ARIA-атрибуты — не настройки.** `aria-*` и `role` — атрибуты хоста. База
читает их для доступного имени и передаёт элементу, который несёт роль;
манифест не объявляет их настройками. Другие имена прототипа, которые
встречаются в поставляемых манифестах (`title`, `prefix`, `blur`,
`spellcheck`), переименовываются с псевдонимами с датой.

`state` не зарезервирован: это слово словаря для состояния данных. Свои
служебные поля рантайм держит закрытыми (`#fields`), а наружу показывает
только базовый интерфейс.

## Регистр имён

| Где | Регистр | Пример |
|:---|:---|:---|
| Манифест, атрибуты, ключи данных, правила | kebab-case | `has-more`, `only-active` |
| Свойства в JavaScript | camelCase | `hasMore` |
| Поля `detail` события | camelCase на элементе, kebab-case в манифесте | `inheritedValue` / `inherited-value` |

Одно выводится из другого при построении; автор пишет только одну форму.

## Полный манифест

Манифест переключателя из стандарта. Он называет семью, источники
доступного имени, действие каждой клавиши и одну открытую CSS-переменную
(у настоящего компонента их 5–10):

```json
{
  "id": "smart.switch",
  "tag": "sf-switch",
  "version": "1.2.0",
  "kind": "leaf",
  "family": "switch",
  "traits": ["field-inherit@1"],
  "settings": {
    "size": {"type": "enum", "values": ["1/2", "1", "2"], "default": "1"},
    "label": {"type": "string", "slot": "label"},
    "help": {"type": "icon"},
    "name": {"type": "string"},
    "value": {"type": "string", "default": "on"}
  },
  "values": {
    "checked": {"type": "boolean", "optional": true, "default-from": "checked", "reflect": true},
    "effective-checked": {"type": "boolean", "summary": "What the person sees, the inherited state included"}
  },
  "events": {
    "change": {"carries": "native"}
  },
  "actions": {},
  "form": {"value": "checked", "submits": "value", "reset": "default"},
  "templates": {"default": {"file": "template.html"}},
  "styles": "styles.scss",
  "examples": "examples.json",
  "docs": "docs.md",
  "lang": "lang/",
  "accessibility": {"role": "switch", "name": {"from": ["label", "slot:label", "aria-label"]},
                    "keys": {"Tab": "reach", "Space": "toggle:checked"}},
  "host-states": {"data-inherited": "boolean"},
  "css-variables": {"--sf-switch-checked-background-color": {"type": "color", "state": "checked"}}
}
```

| Поле | Что задаёт | Где подробнее |
|:---|:---|:---|
| `id`, `tag`, `version`, `kind`, `family`, `package` | кто это, семья, пакет и версия интерфейса | [Имена и общие слова](/ru/guide/smart-components-2/names/), [Пакеты партнёров и проектов](/ru/guide/smart-components-2/packages/) |
| `traits`, `implements` | подключённые общие черты и интерфейсы, которые компонент реализует | [Поля форм](/ru/guide/smart-components-2/forms/), [Слоты](/ru/guide/smart-components-2/slots/) |
| `settings`, `values`, `events`, `actions` | интерфейс | [Модель компонента](/ru/guide/smart-components-2/model/) |
| `form`, `validity` | как компонент участвует в форме | [Поля форм](/ru/guide/smart-components-2/forms/) |
| `templates`, `presentation`, `styles` | разметка, скелетон и стили | [Разметка и шаблоны](/ru/guide/smart-components-2/markup/) |
| `relations`, `aliases`, `x-rule`, `x-registry` | связи загрузчика, псевдонимы старых имён, правило загрузчика и то, что пока знает только реестр; из них построение делает `rule.js`, `aliases.json` и `smart.manifest.json` | выше, [Имена и общие слова](/ru/guide/smart-components-2/names/) |
| `examples`, `docs`, `lang` | примеры, текст, слова | ниже и [Язык](/ru/guide/smart-components-2/language/) |
| `accessibility`, `keyboard` | роль, имя, действие клавиш, клавиатура по элементам, объявления | [Доступность](/ru/guide/smart-components-2/accessibility/) |
| `host-states`, `css-variables`, `parts` | видимые состояния хоста и то, что страница может перекрасить | [Внешний вид](/ru/guide/smart-components-2/look/) |
| `side-effects`, `port`, `connects` | что компонент делает за своими пределами, порт хоста, шипы | [Модель компонента](/ru/guide/smart-components-2/model/#побочные-эффекты), [Данные с сервера](/ru/guide/smart-components-2/data/) |

**Поля верхнего уровня — закрытый список.** В каноническом порядке: `id`,
`tag`, `version`, `kind`, `family`, `package`, `traits`, `implements`,
`settings`, `values`, `events`, `actions`, `keys`, `roles`, `rules`,
`layouts`, `slots`, `form`, `validity`, `selection`, `entry-state`,
`window`, `computed`, `layer`, `side-effects`, `keyboard`, `port`,
`connects`, `templates`, `presentation`, `styles`, `examples`, `docs`,
`lang`, `accessibility`, `host-states`, `css-variables`, `parts`.

- `keys`, `roles`, `rules` и `layouts` бывают только у сборки; `keys` — это
  всегда данные сборки, а клавиатура записывается в `keyboard`.
- Вид папки 1.4 добавляет в манифест `relations` и `aliases` — то, что
  раньше жило в `rule.js` и `aliases.json`.
- Поле не из списка — ошибка, если оно не начинается с `x-`. Поля `x-`
  принадлежат инструментам (`x-studio` хранит положение на холсте,
  `x-rule` и `x-registry` читает построение): их сохраняют, но не проверяют
  и не читают во время работы.
- `$comment` допустим в любом объекте.

Действия `set-checked` у переключателя нет: запись `checked` как настройки
делает то же самое.

## Сохранённый вид манифеста

Манифест пишут люди, Студия и ИИ, поэтому вид файла задан стандартом:

- JSON в UTF-8, переводы строк LF, без BOM, с переводом строки в конце.
- **Новый файл** печатается в каноническом виде: отступ в два пробела, поля
  верхнего уровня — в порядке закрытого списка, члены `settings`, `values`,
  `events`, `actions`, `keys` и `roles` — в порядке автора, `rules` — в
  порядке списка. Два инструмента печатают один манифест одинаковыми
  байтами.
- **Существующий файл** сохраняется с сохранением байтов: всё, что не
  менялось, остаётся байт в байт — пробелы, запись чисел вроде `0.50`,
  экранирование. Печатается только изменённое, с отступом соседей. Открыть
  и сохранить без правок — те же байты.
- **Порядок правил сохраняется.** Новое правило встаёт туда, куда его
  поставил автор, рядом с правилами того же события. Правила сопоставляются
  по `id`, а не по месту в списке.
- **Ключ, записанный в объекте дважды**, отклоняется. Проверка читает это из
  текста: `JSON.parse` молча оставляет последний.

На стенде простое «разобрать и напечатать» переписало 234 строки манифеста
при сохранении без правок. Печать с сохранением байтов (около 250 строк кода)
не переписала ни одной, а пять правок изменили 24 строки.

## Отпечаток договора

Построение считает **отпечаток** интерфейса — SHA-256 от канонического вида
`settings`, `values`, `events` с переносимыми полями, `actions` с
параметрами, `slots`, `traits` и `implements`. Имена и типы входят в
отпечаток, значения по умолчанию, слова и примеры — нет. Отпечаток пишется в
запись реестра рядом с `version`; автор его не пишет.

- **Файл блокировки построения** хранит для каждой детали, которую ставит
  сборка, версию и отпечаток, с которыми сборку построили.
- **При загрузке и при обновлении** рантайм и Студия сравнивают отпечаток
  поставленной детали с отпечатком из файла блокировки:
  - равны — делать нечего;
  - различаются — интерфейсы сравниваются по членам, и в журнал пишется, что
    изменилось: член убран или добавлен, сменился тип, переносимое поле или
    параметр;
  - изменился член, которым пользуется сборка (связь, повод правила `on`,
    переносимое поле, которое читает правило, действие, которое просит
    правило), — деталь отклоняется с причиной `missing-setting`,
    `missing-event`, `carries-mismatch` или `major-mismatch` и обеими
    версиями;
  - любое другое изменение — заметка в журнале.
- Повод и переносимые поля каждого правила сверяются с объявленными
  событиями поставленной детали ещё и при загрузке. На стенде поломка
  содержимого события прошла загрузку и проявилась только на первом событии.

Роль может назвать старшую версию своей детали: `"part": "sf-table@2"`.
Деталь другой старшей версии отклоняется при загрузке с причиной
`major-mismatch` и обеими версиями. Без версии роль берёт ту, что в файле
блокировки. Как роль называет деталь, описано на странице
[Сборки](/ru/guide/smart-components-2/assemblies/#роли-и-связи).

## Примеры и что лежит рядом

`examples.json` — именованные примеры: настройки и ожидаемый результат
(`expect`). Один файл питает Студию, документацию и тесты.

У примера сборки есть сценарий — список шагов, каждый из которых один из
трёх:

| Шаг сценария | Что делает |
|:---|:---|
| `{"fire": "<роль>.<событие>", "with": {…}}` | событие детали |
| `{"set": "<настройка>", "to": …}` | родитель пишет настройку |
| `{"act": "<действие>", "with": {…}}` | родитель просит действие |

`expect` такого примера содержит `values` — значения сборки после сценария
— и `events` — глаголы, которые она отправила наружу, по порядку.

```json
{"name": "open-a-record",
 "settings": {"collection": "orders"},
 "script": [{"fire": "list.open", "with": {"id": "42"}}],
 "expect": {"values": {"selected": "42"}, "events": ["open"]}}
```

Рядом с `examples.json` в папке компонента:

| Файл | Зачем |
|:---|:---|
| `probe.json` | проба соответствия: компонент проверяется в браузере тем же способом, что и на стендах стандарта; с 1.4 её генерирует построение из `pages` в `examples.json` |
| записанные ответы хоста | для компонента с портом: проверка проигрывает их через сгенерированный адаптер |
| `baseline.json` | известные сбои, если они есть |

Каждый известный сбой в `baseline.json` называет проверку, пример или
проверяемый случай и ссылку: задачу или раздел стандарта, который это
разрешает. Сбой без ссылки известным не считается.
