# Пакеты партнёров и проектов

Компоненты SIMAI делают в SIMAI Framework и ui-pro, а партнёр или проект
заказчика может выпустить **свой пакет** компонентов. Страница описывает,
кто может выпускать пакет, как называются его компоненты, как они входят в
сборки SIMAI и что проверяется.

## Кто выпускает пакет

| Кто | Может ли выпустить свои компоненты |
|:---|:---|
| SIMAI Framework | да: базовые компоненты, приставка `sf-` |
| ui-pro | да: продвинутые и общие компоненты, приставка `sf-` |
| Продукт SIMAI: Larena, решения Bitrix, почта, чат | нет: нужный компонент делают в ui-pro |
| Партнёр, проект заказчика | да: пакет под своей приставкой |

Пакет зависит от SIMAI Framework или ui-pro, а не наоборот: компоненты SIMAI
о пакетах партнёров ничего не знают. Пакет — это компоненты, которые
выпускаются и версионируются вместе под одной приставкой.

## Своя приставка

- У пакета своя приставка, и её берёт каждый тег пакета: `acme-map`,
  `acme-route-list`.
- Приставка никогда не `sf-` и не `simai-` и не слово из списка
  `naming-words.json`.
- Остальные правила имён те же: главное слово в конце, не больше трёх слов
  после приставки, семья в поле `family` — см.
  [Имена и общие слова](/ru/guide/smart-components-2/names/).
- События компонента пакета называются по его тегу: `acme-map-pick`.

## Поле `package` в манифесте

Манифест компонента пакета называет свой пакет:

```json
{
  "id": "acme.map",
  "tag": "acme-map",
  "version": "1.4.0",
  "kind": "leaf",
  "family": "map",
  "package": {"name": "acme-widgets", "version": "1.2.0", "prefix": "acme"},
  "implements": ["acme-map-view@1"],
  "settings": {"points": {"type": "list", "of": {"id": "id", "title": "string"}}},
  "events": {"pick": {"carries": {"id": "id"}}}
}
```

Компонент SIMAI поле `package` может не писать.

## Вход только через интерфейс

Компонент пакета входит в сборку SIMAI только через интерфейс
`<имя>@<старшая версия>`:

- через **слот с `accepts`** — его ставит страница;
- через **роль с `accepts`** — его ставит сама сборка. Роль может ещё и
  назвать деталь со старшей версией: `"part": "acme-map@1"`.

```json
"roles": {
  "map": {"accepts": "acme-map-view@1", "part": "acme-map@1",
          "bind": {"settings.points": "points"}}
},
"rules": [
  {"id": "r-pick", "on": "map.pick", "steps": [{"set": "chosen", "to": {"from": "id"}}]}
]
```

Интерфейс, который определил пакет, несёт приставку пакета:
`acme-map-view@1`. Интерфейс, который публикует SIMAI, приставки не несёт:
`record-view@1`. Деталь, которая не реализует интерфейс или реализует его
другую старшую версию, отклоняется с причиной из того же списка, что у
слотов: `no-interface`, `other-interface`, `major-mismatch` и другие.

## Реестр элементов на старшую версию пакета

- Рантайм определяет теги пакета в **отдельном реестре пользовательских
  элементов** (scoped custom element registry) на каждую старшую версию
  пакета. Поэтому две старшие версии одного пакета работают на одной
  странице.
- Статическая разметка разбирается браузером в общий реестр, поэтому в
  первом кадре страницы у каждого тега одна старшая версия.
- Где браузер не умеет отдельных реестров, на странице живёт одна старшая
  версия тега.

На стенде пакеты `acme-widgets` 1.2.0 и 2.0.0 работали на одной странице
через отдельные реестры (Chromium 149), а сборка, построенная под `@1`, на
странице только с `@2` была отклонена с причиной `major-mismatch` и обеими
версиями.

## Те же проверки

Пакет проходит те же проверки, что компонент SIMAI. Отличается одна —
проверка имён: она читает приставку пакета и его собственный список имён
вместо реестра `sf-`, а манифест обязан назвать `package`. Подробно — на
странице [Проверки](/ru/guide/smart-components-2/quality/).
