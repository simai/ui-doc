# Правила

Логика сборки — **упорядоченный список правил**. Правило говорит: когда
случилось это событие, выполни шаги по порядку, только если условие
выполнено. В Студии это окно «Когда → Только если → Сделать». Связи держат
состояние, а правила обрабатывают моменты.

## Устройство правила

```json
{"id": "r-delete", "on": "trash.press", "concurrency": "drop",
 "if": {"left": {"key": "chosen"}, "op": "filled"},
 "steps": [
   {"do": "source.delete", "with": {"ids": {"key": "chosen"}}},
   {"add": "removed", "by": {"value": 1}},
   {"reset": "chosen"}
 ],
 "otherwise": [{"do": "toast.show", "with": {"text": {"value": "Не удалось удалить"}}}]}
```

| Поле | Слово в Студии | Что значит |
|:---|:---|:---|
| `id` | — | код правила, обязателен и уникален в манифесте: по нему работают журнал, защита от петель и сохранение в Студии |
| `on` | Когда | повод — событие, которое правило слушает |
| `if` | Только если | условие; если не выполнено, правило пропускается целиком |
| `steps` | Сделать | шаги по порядку |
| `otherwise` | Иначе | шаги на случай, если хост ответил `conflict`, `refused` или `unavailable` |
| `concurrency`, `timeout`, `retry` | — | как перекрываются запуски, сколько ждать и сколько повторять — см. ниже |

## Поводы

| Запись `on` | Когда срабатывает |
|:---|:---|
| `<роль>.<событие>` | событие части: `list.open`, `trash.press` |
| `outside.<действие>` | сборку попросили выполнить действие |
| `outside.<настройка>` | изменилась настройка сборки |
| `data.<ключ>` | изменился ключ — любой, кроме ключа с хозяином `parent`: его изменение слышат как `outside.<настройка>` |

`outside.<настройка>` и `data.<ключ>` несут `{value, previous}`, и
`{"from": "value"}` читает новое значение.

## Шаги

| Шаг | Что делает |
|:---|:---|
| `{"do": "<роль>.<действие>", "with": {…}}` | просит часть выполнить действие |
| `{"set": "<ключ>", "to": чтение}` | пишет ключ, которым владеют правила |
| `{"add": "<ключ>", "by": чтение}` | прибавляет к числовому ключу |
| `{"reset": "<ключ>"}` | возвращает ключ к начальному значению |
| `{"emit": "<событие>", "with": {…}}` | отправляет наружу событие сборки |
| `{"check": условие}` | идёт дальше, только если условие выполнено, иначе заканчивает правило |
| `{"refuse": {"reason": …}}` | отклоняет отклоняемую просьбу, которую слышит правило; такое правило выполняется сразу и не ждёт |
| `{"ask": "<роль>.open", "with": {…}, "answer": "<ключ>"}` | открывает окно и ждёт ответа человека `{accepted, reason, value}`, который пишет в ключ |
| `{"append": "<ключ-список>", "item": чтение}` | добавляет запись в конец списка, которым владеют правила; у записи есть `id` |
| `{"remove": "<ключ-список>", "id": чтение}` | убирает из такого списка запись с этим кодом |

**Шаги — закрытый список.** Шаг не из таблицы не пропускает проверка 5.
Новый шаг появляется только с новой версией стандарта и только когда стенд
показал, что его не сделать деталью, производным ключом или чтением. Всё
остальное — цикл, расчёт, обращение к сервису — это код детали в
`behaviour.js`, до которого правило доходит через действие.

## Когда выполняется «иначе»

Ветка `otherwise` выполняется, только когда шаг, который ждёт, получил
`conflict`, `refused` или `unavailable`. Правило, пропущенное по `if`, и
правило, которое закончил неудачный `check`, больше ничего не выполняют.
Шаг `ask` отвечает `applied`, что бы ни выбрал человек; дальше правило
читает `answer.accepted`.

## Чтения: откуда берётся значение

| Чтение | Откуда |
|:---|:---|
| `{"from": "<поле>"}` | поле того, что принесло событие |
| `{"key": "<ключ>"}` | ключ сборки; путь через точку читает поле ключа-объекта: `answer.accepted` |
| `{"value": …}` | постоянное значение своего типа |
| `{"entry": "<поле>"}` | поле записи, чья деталь отправила событие (роль на каждую запись) |
| `{"new": "id"}` | новый код для новой записи: уникальный на странице, не счётчик; записанный, он не меняется |
| `{"object": {"<поле>": чтение, …}}` | объект из чтений: для содержимого просьбы, отправки или производного ключа |
| `{"sum": [чтение, …]}`, `{"difference": [чтение, чтение]}`, `{"product": [чтение, …]}` | сумма, разность, произведение; незаданное или `null` даёт `null` |
| `{"count": чтение}` | число записей в списке |
| `{"choose": условие, "then": чтение, "else": чтение}` | одно из двух чтений по условию |

Условие может стоять везде, где читается да или нет.

## Условия

Условие записывается как `{"left": чтение, "op": операция, "right": чтение}`.

| Операция | Значит | Нужен `right` |
|:---|:---|:---|
| `eq`, `ne` | равно, не равно | да |
| `gt`, `lt` | больше, меньше | да |
| `has` | содержит | да |
| `filled`, `empty` | заполнено, пусто | нет |
| `yes`, `no` | да, нет | нет |

`{"all": [условие, …]}` выполнено, когда выполнены все, `{"any": [условие,
…]}` — когда выполнено хотя бы одно. `if` пропускает всё правило; `check`
заканчивает его посередине.

Чтения и условия — такие же закрытые списки, как шаги: ни выражений, ни
склейки строк (слова берутся из файлов слов), ни функций.

## Как выполняются правила

1. **Ход** — одно событие и все правила, которые его слушают, в порядке
   списка. Шаги правила идут по порядку.
2. **Записи копятся.** Записи ключей за ход применяются вместе в его конце,
   затем связи несут новые значения частям и наружу через `values`. Шаг
   читает несохранённые записи своего хода раньше применённых.
   - **Шаг, который ждёт, сначала применяет записи своего хода**, сделанные
     до него, и связи сразу их несут. Остальные применяются в конце хода.
     Так кнопка «Остановить» появляется, пока чат ждёт ответа, а не после.
3. **Ожидание.** Шаг, который обращается к хосту (источник, сохранение),
   ждёт ответа: `applied`, `conflict`, `refused` или `unavailable`.
   - Дальше правило идёт только при `applied`.
   - `conflict`, `refused` или `unavailable` заканчивает шаги правила,
     запускает его `otherwise` и пишется в журнал вместе с `message` хоста.
   - `cancelled` — запуск остановил человек, его заменил более новый запуск
     или закончилась область экземпляра — заканчивает шаги без `otherwise`.
     Журнал записывает поступок, а не сбой.
   - Действие, которое начинает поток, отвечает, когда поток начался, а не
     когда закончился.
   - Собственное событие-факт источника (`saved`, `deleted`) — новый ход.
4. **Пессимистично по умолчанию.** Данные меняются после `applied`.
5. **Петли.** Правило не запускается дважды по одной причине: каждый ход
   несёт цепочку правил, которые к нему привели. Цепочка обрывается на
   глубине 32, и обрыв — ошибка в журнале, а не тишина. Каждый шаг `emit`,
   который выносит событие детали из сборки, добавляет к цепочке звено,
   поэтому событие проходит не больше 32 рамок, а обрыв называет самый
   глубокий экземпляр. Равное значение повторно не пишется. Цикл связей
   между уровнями не пропускает построение.
6. **Асинхронный ответ несёт свою причину.** Ответ источника начинает свой
   ход с цепочкой того хода, который спрашивал, поэтому защита от петель
   работает и через ожидание. Данные, которые порт прислал сам, без просьбы,
   начинают ход с пустой цепочкой.

:::diagram {engine=mermaid title="Шаг, который обращается к хосту, ждёт ответа: при applied правило идёт дальше, при отказе выполняется otherwise, при отмене — ничего"}
sequenceDiagram
    participant trash as Кнопка «Удалить»
    participant asm as Сборка
    participant src as Источник
    participant host as Хост
    trash->>asm: событие trash.press
    asm->>src: do source.delete
    src->>host: запрос
    host-->>src: ответ
    alt applied
        src-->>asm: applied
        asm->>asm: следующие шаги
    else conflict, refused или unavailable
        src-->>asm: отказ с причиной
        asm->>asm: ветка otherwise и запись в журнал
    else cancelled
        src-->>asm: отменено
        asm->>asm: шаги закончены, otherwise не выполняется
    end
:::

## Одновременные запуски

Пока ход ждёт, новые события начинают новые ходы, и один и тот же запуск
может пойти дважды: второе сообщение уйдёт, пока первое ещё отправляется.
Правило или действие детали объявляет, как перекрываются его запуски. Это
одна настройка с одинаковыми полями в обоих местах:

```json
{"id": "r-send", "on": "composer.submit", "concurrency": "drop", "timeout": 30000,
 "steps": [{"do": "source.submit", "with": {"values": {"key": "draft"}}}]}
```

| `concurrency` | Новый запуск, пока прежний ждёт |
|:---|:---|
| `parallel` (по умолчанию) | идёт тоже |
| `queue` | ждёт, пока прежний закончится; запуски сохраняют порядок |
| `drop` | отбрасывается; отклоняемая просьба получает отказ с причиной `busy` |
| `latest` | заменяет прежний: его шаг, который ждёт, отвечает `cancelled`, а его запрос прерывается |

- **Никогда `latest` для изменения.** Прерванное изменение могло уже
  выполниться на хосте. Правило, чей ждущий шаг — изменение (`save`,
  `delete`, `submit` и другие глаголы-изменения словаря), и действие-изменение
  берут `parallel`, `queue` или `drop`; `latest` там не пропускает
  проверка 5.
- **Изменение несёт свою личность:** `revision` записи и `client-key`.
  Ключ делает источник, а не правило; повтор с тем же ключом — то же
  изменение.
- **`timeout`** в миллисекундах: шаг, который ждёт дольше, отвечает
  `unavailable` с причиной `timeout`, а его запрос прерывается.
- **`retry`** — `{"times": n, "delay": мс}`: чтение повторяется при
  `unavailable`; изменение — только если несёт `client-key`, и с исходной
  версией. `refused` и `conflict` не повторяются никогда.
- Каждый запрос, поток и ожидание привязаны к области экземпляра, поэтому
  `latest`, `timeout` и удаление экземпляра прерывают их одинаково.
- Журнал записывает каждый ход, который начался, пока ждал другой ход той
  же шины, и что сделала с ним настройка.

Источник применяет только самый новый ответ — это `latest` на его чтениях.

## Событие, которое ждёт

Событие с `"waits": true` — тот же договор ожидания, только со стороны
детали. Деталь отправляет событие, помечает у записи `write: pending` для
названных полей и ждёт исхода через своё действие
`settle {id, answer, record}`. При любом ответе, кроме `applied`, она
показывает запись такой, какой её держит хост, и помечает `write: failed`.
Так устроена запись в ячейке таблицы — см.
[Записи: строки и узлы](/ru/guide/smart-components-2/entries/). Ответ
человека на `ask` ждут так же, и он сохраняет цепочку причин.

## Оптимистичные ключи и несколько изменений сразу

- Ключ может быть `"optimistic": true`: изменение видно сразу, снимок
  сохраняется, а отказ хоста восстанавливает снимок и помечает запись
  `write: failed`.
- Несколько изменений, которые должны пройти вместе, — это **одно**
  сохранение у хоста, и поэтому оно атомарно. Интерфейс не склеивает
  несколько просьб в транзакцию.

## Разобранные примеры

**Открыть запись и сообщить родителю.**

```json
{"id": "r-open", "on": "list.open",
 "steps": [{"set": "chosen", "to": {"from": "id"}},
           {"emit": "open", "with": {"id": {"from": "id"}}}]}
```

Когда список сообщил `open {id}`, правило пишет код в `chosen` и отправляет
наружу собственное событие сборки `open` с тем же кодом. Значение `selected`
сборки, привязанное к `chosen`, обновится в конце хода.

**Удалить после подтверждения.**

```json
{"id": "r-trash", "on": "trash.press", "concurrency": "drop",
 "if": {"left": {"key": "chosen"}, "op": "filled"},
 "steps": [
   {"ask": "confirm.open", "with": {"text": {"value": "Удалить запись?"}}, "answer": "answer"},
   {"check": {"left": {"key": "answer.accepted"}, "op": "yes"}},
   {"do": "source.delete", "with": {"ids": {"key": "chosen"}}},
   {"reset": "chosen"}
 ],
 "otherwise": [{"do": "toast.show", "with": {"text": {"value": "Не удалось удалить"}}}]}
```

Если ничего не выбрано, правило пропускается. Иначе открывается окно
подтверждения; если человек не подтвердил, `check` заканчивает правило без
ветки «иначе». Если хост ответил `conflict`, `refused` или `unavailable`,
`reset` не выполняется, а срабатывает ветка «иначе». Повторное нажатие, пока
удаление идёт, отбрасывается.

**Не дать закрыть панель с несохранённым.**

```json
{"id": "r-keep-open", "on": "panel.close",
 "if": {"left": {"from": "unsaved"}, "op": "yes"},
 "steps": [{"refuse": {"reason": {"value": "unsaved"}}}]}
```

Панель отправляет отклоняемую просьбу `close`; правило с `refuse`
выполняется сразу, и действие панели отвечает `refused`.

**Добавить и убрать контакт в форме.**

```json
[{"id": "r-add-contact", "on": "add.press",
  "steps": [{"append": "contacts", "item": {"object": {"id": {"new": "id"}, "name": {"value": ""}}}}]},
 {"id": "r-drop-contact", "on": "contact.detach",
  "steps": [{"remove": "contacts", "id": {"entry": "id"}}]}]
```

Первое правило добавляет пустой контакт с новым кодом, и роль `contact` с
`each` сразу ставит для него строку. Второе слышит `detach` от любой строки
и убирает ту запись, чья строка его отправила.

**Обновить по просьбе снаружи и посчитать обновления.**

```json
{"id": "r-refresh", "on": "outside.refresh",
 "steps": [{"do": "source.refresh"}, {"add": "refreshed", "by": {"value": 1}}]}
```

**Вернуться на первую страницу при новом запросе.**

```json
{"id": "r-first-page", "on": "data.query", "steps": [{"do": "pagination.reset"}]}
```

Новый запрос сам страницу не сдвигает: на первую страницу её возвращает
правило.

## Правило в Студии

В Студии правило — одна пара точек и один провод: точка выхода на части, чьё
событие оно слушает, и точка входа на части, которую просит его первый шаг.
Изменение одного правила никогда не трогает другое. Точки и провода — только
способ нарисовать правило: сохраняется список, и порядок правил на одно
событие — это порядок списка.
