# Стандарт: динамический композитный компонент

`simai.dynamic-composite-component`, версия 1.0.0.

Это тот же композитный компонент, но связанный с сервером приложения: он
показывает записи, сохраняет настройки и просит выполнить действия. Стандарт
описывает границу между компонентом и приложением: кто чем владеет, как
компонент просит, как приложение отвечает и что происходит при конфликте.

Стандарт наследует [композитный компонент](/ru/reference/standards/composite-component/)
1.0.0: все его требования действуют и здесь, повторно они не перечисляются.
Роли полей, типы представлений и модель запроса — это уже профиль поверх этого
стандарта, а не он сам.

## Требования

| Идентификатор | Уровень | Требование |
|:---|:---|:---|
| `structure-and-data-separated` | обязательно | Структурные свойства и данные запроса идут разными каналами. Данные принимаются только через свойства, объявленные как связанные с запросом. |
| `request-data-not-persisted` | обязательно | Данные запроса никогда не сохраняются как определение, рецепт или общий снимок. |
| `intent-not-patch` | обязательно | Компонент сообщает намерение, решение принимает и проверяет приложение. Компонент не отправляет правку сохранённого документа. |
| `intent-payload-exact` | обязательно | Содержимое намерения проверяется по точному набору ключей: неизвестный или пропущенный ключ отклоняется. |
| `intent-carries-no-transport` | обязательно | Намерение называет, что попросил человек и каких записей это касается. В нём нет адреса, запроса, токена и других деталей доставки: способ запроса выбирает приложение. |
| `identity-by-reference` | обязательно | Идентификаторы из браузера — только ссылки. Приложение само перечитывает сохранённые байты и ревизии. |
| `mutation-carries-revision` | обязательно | Каждое изменение несёт ревизию, которую браузер видел последней. Изменение без ревизии отклоняется. |
| `server-compares-revision` | обязательно | Приложение сравнивает ревизию под блокировкой и на конфликт отвечает текущей ревизией. Молча перезаписывать нельзя. |
| `conflict-keeps-draft` | обязательно | При конфликте компонент сохраняет несохранённый ввод человека и предлагает обновить данные, а не выбрасывает его. |
| `batch-all-or-nothing` | обязательно | Групповое изменение отклоняется целиком, если хотя бы у одной записи ревизия устарела. |
| `sequenced-responses` | обязательно | Каждый экземпляр нумерует свои запросы и отбрасывает ответ, который старше последнего отправленного запроса. |
| `dispose-releases` | обязательно | Уничтожение экземпляра отменяет его подписки и незавершённые запросы и не задевает другие экземпляры. |
| `settings-layers` | обязательно | Настройки разрешаются в определённом порядке: значения пакета, затем общие (системные или командные), затем личные. Поля, которые может задавать только общий слой, объявлены. |
| `reset-is-a-write` | обязательно | Сброс настройки — это запись со сравнением ревизии, которая двигает ревизию вперёд, а не удаление. |
| `shared-and-personal-separated` | обязательно | Общие и личные настройки идут через разные адреса с разными правами, а владелец настроек берётся из сессии, а не из тела запроса. |
| `endpoints-are-relative` | обязательно | Адреса в свойствах — относительные пути без схемы, узла и строки запроса. Принятый путь сам по себе не даёт доступа. |
| `honest-unavailable` | следует | Без своего серверного адреса компонент прямо сообщает, что возможность не подключена. Незавершённая операция никогда не показывается как выполненная. |
| `shared-state-in-link` | следует | Состояние, которое другой человек должен увидеть по ссылке, живёт в адресе. Личные удобства могут оставаться в браузерном хранилище. |
| `data-states-declared` | следует | Компонент объявляет свои состояния данных (как минимум загрузка, есть данные, пусто, ошибка) и показывает текущее. Пока запрос выполняется, он не рисует придуманные данные. |

## На чём стандарт стоит

- композитный компонент 1.0.0 — наследуется целиком, закреплён по точным
  байтам;
- манифест Smart-компонента (схема v2) — он уже описывает хранение, владение,
  безопасность, готовность, события и состояния; этот стандарт добавляет то,
  чего там нет: личность экземпляра, жизненный цикл, порядок ответов, слои
  настроек и поведение при конфликте.

## Как проверяется

Проверка ручная: автор компонента показывает, чем выполнено каждое требование.
Черновик подготовила команда Larena на списке записей CMS, административном меню
и редакторе страниц; требования Framework добавлены при издании.
